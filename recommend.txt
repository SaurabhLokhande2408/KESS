# WEBSITE PERFORMANCE OPTIMIZATION RECOMMENDATIONS

## 1. Executive Summary

This is a Next.js 14 Pages Router site with eight routes, a shared app wrapper, statically imported JSON content, shared navigation/footer, and a FastAPI backend used only when contact or career forms are submitted. No analytics tags or client-side data fetches are present on page load. The two Google font families are configured with `next/font/google`, which self-hosts their generated font files in the Next build rather than making a browser request to Google Fonts on each visit.

The strongest source-confirmed opportunities are resource-loading issues, not a need to remove content:

- `Footer` embeds an eager, high-priority Google Maps iframe on every route.
- The global loader prewarms several assets unrelated to the current route. The Services and Training route maps point to images those pages do not render. Warmup also requests original image URLs while `next/image` can request separately optimized URLs for the same content.
- The Gallery page statically renders 23 images and explicitly marks every gallery image eager. Their original files total 51,094,196 bytes (about 51.1 MB); actual optimized transfer size is not measurable from source alone.
- Services uses six raw `<img>` tags marked eager/high priority, with no `srcset`; the `sizes` attribute on those `<img>` tags cannot select responsive sources. Their original files total 10,690,435 bytes (about 10.7 MB).
- Training uses three raw `<img>` elements for two unique large PNGs without lazy-loading or responsive source hints. The two unique source files total 5,063,189 bytes.
- The Home hero and logo have smaller WebP alternatives already in `public`, but current components reference the larger PNG versions.

No Lighthouse scores, CWV values, request counts, decoded memory, production cache headers, or device/network timings are claimed here. They require a production build/deployment and browser measurements.

## 2. Performance Philosophy

Preserve 100% of existing content, UI, layout, branding and functionality while reducing the amount of work required to display and operate the website.

All recommendations below retain the current imagery, map, fonts, page content, animations, navigation, and interactions. Optimizations should change delivery and scheduling, not the visual result.

## 3. Current Architecture

- Frontend: Next.js 14.2.35, React 18.3.1, Pages Router. Routes are `index`, `about`, `services`, `training`, `gallery`, `clients`, `careers`, and `contact` under `frontend/pages`.
- `frontend/pages/_app.js` imports global Tailwind CSS, configures Fraunces and Inter through `next/font/google`, and renders `GlobalLoader` around every page. `_document.js` sets the document shell and a PNG favicon.
- Each route renders its own page markup and commonly imports `Navbar`, `Footer`, `SEO`, and `FloatingWhatsApp`. `siteData.json` supplies shared company, client, service, career, training, and contact content. There is no React context/store or general data-fetching layer.
- The Home page additionally renders two `ClientMarquee` instances, `StatBar`, `WhyTrustKESS`, and `Differentiator`. Services and Training include substantial route-local markup and CSS animations. Gallery uses `getStaticProps` to enumerate every supported image in `public/images/images_company` at build time.
- `next/image` is used for the shared logos, `PageHero`, and gallery. Services, Training, Clients, and the founder image in `Differentiator` use raw `<img>` elements. `next.config.js` retains the default Next image optimizer settings and permits Unsplash, though no current page/data source references an Unsplash image.
- Backend: FastAPI with contact and career submission endpoints, CORS, in-memory rate limiting, and SMTP email delivery. The frontend makes `fetch` POST requests only after explicit form submission; there is no page-load API request.
- No analytics, video assets, service worker, or repository deployment configuration for cache headers was found. The repository has no Vite/Webpack customization; Next handles page chunks and build output.

## 4. Critical Performance Bottlenecks

### 4.1 Global eager map embed

Priority: P1 (high)
Evidence: Confirmed source behavior; network cost needs measurement.

File: `frontend/components/Footer.jsx`, `frontend/components/GoogleMap.jsx`
Component: `Footer` -> `GoogleMap`
Current behavior: `Footer` is rendered on every route. Its map iframe uses `loading="eager"` and `fetchPriority="high"` and points to Google Maps. The map is in the footer, after the page content.
Problem: Every first page visit can initiate an external Google Maps request even though the map is far below the initial viewport. It competes with the current page's own text, fonts, and images, adds a third-party connection, and repeats this behavior across all eight routes. Exact request count and Google response cost require a waterfall.
Recommended change: Preserve the same map and footer layout, but let the iframe load lazily near the viewport and do not assign it high fetch priority. If measurement still shows a cost, defer creating the iframe until it is near view while preserving its exact dimensions and map URL.
Expected impact: Less third-party work during initial rendering and less contention on slow mobile networks; no change to map availability when the user reaches the footer.
Risk: Low. Verify the map still loads reliably when scrolled into view and after client-side route navigation.
UI/UX impact: None intended; same embedded map, dimensions, position, and interaction.
Implementation difficulty: Low.
Affects: Initial load: yes; page navigation: yes; mobile: yes; slow network: high benefit; CPU: possible reduction in third-party work; memory: likely reduction before footer is reached; bundle size: no.

### 4.2 Global loader fetches unrelated and duplicate image URLs

Priority: P1 (high)
Evidence: Confirmed source behavior; the extent of contention requires a waterfall.

File: `frontend/components/GlobalLoader.jsx`, `frontend/lib/routeCriticalAssets.js`, `frontend/components/PageHero.jsx`
Component: `GlobalLoader`
Current behavior: The initial loader covers the entire viewport and locks scrolling. On route readiness it waits for `warmImageSet` or a 2,000 ms timeout. Home's critical set is the hero plus all 17 client logos. The route map also assigns `hero_bg.png` to `/services` and `g_bg.png` to `/training`, although those pages do not render either file. On every route, `doBackgroundWarmup` schedules the Home hero, gallery hero, About hero, logo, and all client logos, using `requestIdleCallback` or a 150 ms timeout. `warmImage` creates native `Image` elements with raw public URLs. Elsewhere, `next/image` normally requests a transformed `/_next/image` URL.
Problem: The Services and Training loader gates can wait for unrelated original images. Global warmup can consume bandwidth with several routes' assets before they are needed. Where the same image is also rendered through `next/image`, the raw warmup URL is distinct from the optimized URL and can cause a second representation to be downloaded. The Home gate also waits for every client logo, not only its hero. A 2-second timer is a configured upper bound for the initial critical-image gate, not a measured user delay.
Recommended change: Keep the same loader appearance and route-transition behavior, but make route-critical lists match assets actually rendered above the fold on each route. Do not gate on below-fold client logos. Limit background warming to genuinely likely next-route assets, run it only when the browser is idle and the connection/data-saving state permits it, and warm the same optimized URL that the component will use (or avoid warming an image already handled by `next/image`). Keep a bounded fallback for unavailable assets.
Expected impact: Fewer unnecessary requests and less loader waiting on slow connections; reduced contention for actual page imagery, especially on Home, Services, and Training.
Risk: Medium. Loader timing is user-visible; preserve the current visual sequence and test initial load, successful/error route navigation, slow images, and route changes before/after the 2-second fallback.
UI/UX impact: None intended. The loader design and animation remain; only the assets that gate or compete for loading change.
Implementation difficulty: Medium.
Affects: Initial load: yes; page navigation: yes; mobile: high; slow network: high; CPU: image decode savings; memory: image decode savings; bundle size: no.

### 4.3 Gallery eagerly requests all gallery images

Priority: P1 (high)
Evidence: Confirmed `loading="eager"`; transformed transfer bytes and browser scheduling require measurement.

File: `frontend/pages/gallery.js`, `frontend/public/images/images_company/`
Component: `Gallery`
Current behavior: `getStaticProps` includes all 23 supported images in `images_company`. Every grid `<Image>` is explicitly `loading="eager"`, with declared 1200x900 dimensions and a responsive `sizes` value. The 23 original files total 51,094,196 bytes. Next Image optimization can change the delivered format/size, so this source total is not the gallery's measured transfer size.
Problem: The whole portfolio is scheduled when the gallery page renders, including cards well below the fold. On slow connections this can delay the first visible gallery images and consume bandwidth, image decode time, and memory sooner than needed.
Recommended change: Preserve all cards and the lightbox. Use eager/high priority only for the first image or images genuinely visible in the initial viewport; use native/Next lazy loading for the rest, keeping the existing `sizes` behavior. Retain the explicit lightbox selection behavior and request its full-size image only when opened. Review the generated optimizer widths against the rendered card sizes.
Expected impact: The page can become useful after loading its first visible content without waiting for the full portfolio; less initial network and decode work, especially on mobile.
Risk: Low to medium. Verify near-viewport loading does not reveal empty spaces during normal scroll and that opening a lightbox still loads promptly. Do not reduce the gallery or remove any entries.
UI/UX impact: None intended; all images and interactions remain, arriving as the user approaches them.
Implementation difficulty: Low to medium.
Affects: Initial load: high; page navigation: yes when entering Gallery; mobile: high; slow network: high; CPU: decode work deferred; memory: decoded images deferred; bundle size: no.

### 4.4 Services eagerly loads six unoptimized source images

Priority: P1 (high)
Evidence: Confirmed raw `<img>`, eager/high priority attributes, and source asset sizes.

File: `frontend/pages/services.js`, `frontend/public/images/images_company/`
Component: `ServiceImage` rendered for six service rows
Current behavior: All six service photos are raw `<img>` elements with `loading="eager"`, `fetchPriority="high"`, and a `sizes` attribute. Because these elements have no `srcset`, `sizes` does not select a smaller responsive source. The six originals total 10,690,435 bytes: `Security_guarding.jpeg` 220,972 bytes (1600x1200), `hosuekeeping.png` 1,972,741 bytes (1370x1148), `Screenshot 2026-09-18 184202.png` 307,204 bytes (543x320), `on_job_training.png` 2,929,296 bytes (1448x1086), `vip_protection.png` 2,146,949 bytes (1672x941), and `edacf068-cb92-4324-8d77-2af33de64519.png` 3,113,273 bytes (1448x1086). The page hero itself is text-led; these images appear in the subsequent service rows.
Problem: Large original PNGs are requested at high priority even when their service row is far below the initial viewport, and raw `<img>` bypasses Next's built-in responsive image optimizer.
Recommended change: Preserve every service photo and current row. Use Next Image or provide equivalent width-specific `srcset`/`sizes` variants; lazy-load rows below the viewport and reserve eager/high priority only for a service image shown immediately on screen. Keep the existing fixed-height image frame and `object-cover` crop. Convert oversized PNG/JPEG sources to visually equivalent WebP/AVIF or optimized JPEG where appropriate, after checking photographic detail and color.
Expected impact: Smaller image responses at mobile display widths and fewer initial high-priority downloads; less decode and memory work.
Risk: Low to medium. Confirm crop, sharpness, and frame dimensions remain unchanged at each breakpoint.
UI/UX impact: None intended; same six photos, order, crop, and hover interactions.
Implementation difficulty: Medium.
Affects: Initial load: high; page navigation: high on Services; mobile: high; slow network: high; CPU: decode savings; memory: decode savings; bundle size: no.

### 4.5 Home and Clients eagerly load client logos

Priority: P1 on Home; P2 on Clients
Evidence: Confirmed source behavior; actual network deduplication is browser-dependent.

File: `frontend/components/ClientMarquee.jsx`, `frontend/pages/index.js`, `frontend/pages/clients.js`, `frontend/data/siteData.json`
Component: `ClientMarquee`; Clients page logo grid
Current behavior: The Home page renders `ClientMarquee` twice. Each marquee renders the 17 logos twice for its two animation tracks. Each `<Image>` is marked eager and `fetchPriority="high"`; the first four per track are also marked `priority`. The Clients route renders all 17 logos in raw `<img>` elements, also eager and high priority, in a section below its hero. Several source files are large, including `sadhana bank.jpg.jpeg` (602,258 bytes, 1000x786) and `Gateway towers.png` (325,257 bytes, 3000x3000).
Problem: Below-fold client marks are assigned high request priority. On Home, repeated marquee tracks and two instances create many image elements and preload hints. Browsers commonly reuse identical URLs, so this does not prove 68 unique transfers; the actual request count and priority ordering must be inspected in a waterfall. The Clients route's raw `<img>` elements do not use Next responsive optimization.
Recommended change: Keep both marquee sections, all logos, and the animation. Prioritize only the logo instances needed for the first visible marquee viewport; lazy-load remaining logos while preserving the seamless marquee appearance (test its duplicated track at the loop boundary). On Clients, use optimized responsive sources and lazy-load logos below the initial viewport. Avoid setting every logo to high priority.
Expected impact: Fewer competing high-priority requests and lower image transfer/decode work on both routes.
Risk: Medium for the marquee because its duplicate tracks support the animation; low for the static Clients grid. Test the animation and scrolling on mobile.
UI/UX impact: None intended; no logo, section, or animation is removed.
Implementation difficulty: Medium.
Affects: Initial load: high; page navigation: yes; mobile: high; slow network: high; CPU: decode savings; memory: decode savings; bundle size: no.

### 4.6 Large existing PNG/JPEG sources and already-present WebP variants

Priority: P1 (high)
Evidence: Confirmed source byte sizes; visual equivalence is a candidate pending cross-device QA.

File: `frontend/components/PageHero.jsx`, `frontend/components/Navbar.jsx`, `frontend/components/GlobalLoader.jsx`, `frontend/pages/_document.js`, `frontend/public/images/images_used/`, `frontend/public/images/logo/`, `frontend/public/images/team.jpg`
Component: Shared `PageHero`, Navbar, GlobalLoader
Current behavior: Home and Contact pass `/images/images_used/hero_bg.png` to a priority `next/image` hero (1536x1024, 2,393,372 bytes). The About route uses `team.jpg` as a priority hero (2390x1760, 6,636,824 bytes). The WebP files depict the same hero/logo subject when inspected, but are not currently referenced by these components. `PageHero` and the logo components already use `next/image`; they benefit from its optimizer, unlike raw `<img>` usages.
Problem: The source repository retains large originals, and route warmup separately requests raw paths. Risk: Medium until visual and optimizer output comparisons are completed.
UI/UX impact: None intended; exact same hero and logo appearance is a release condition.
Implementation difficulty: Low to medium.
Affects: Initial load: high; page navigation: high; mobile: high; slow network: high; CPU: decode/optimizer work may fall; memory: decoded pixel footprint depends on rendered dimensions; bundle size: no.

### 4.7 Loader animation paint cost (measurement-gated)

Priority: P2 (medium, only if profiling confirms cost)
Evidence: Source shows per-frame filter and SVG stroke-dash changes; dropped frames are not measurable from source alone.

File: `frontend/styles/globals.css`, `frontend/components/GlobalLoader.jsx`
Component: Full-screen loader
Current behavior: The ring continuously animates `filter: drop-shadow`, opacity, SVG `stroke-dasharray`, and transform; three dots animate transform, opacity, and box-shadow. The loader exists globally and is initially visible. `will-change` is applied to loader content/frame/ring.
Problem: Transform/opacity can often stay on the compositor, but animated filters, stroke-dasharray, and shadows can require recurring paint work on constrained GPUs/CPUs. This is a plausible cost, not a demonstrated defect.
Recommended change: Profile the initial loader on a low-end Android device and under CPU throttling. Only if the ring/dots cause paint time or dropped frames, reduce repeated paint work while preserving the same perceived ring, glow, pulse, timing, and reduced-motion behavior (for example, use static effect layers and keep motion on transform/opacity where the rendered result matches).
Expected impact: Lower main-thread/raster work while the loader is visible, if the profile confirms the current animation is costly.
Risk: Medium because the loader is branded and its motion is part of the experience; do not alter it without visual comparison and profiling evidence.
UI/UX impact: Must remain visually and temporally equivalent.
Implementation difficulty: Medium.
Affects: Initial load: yes; page navigation: yes when fallback shows; mobile: high; slow network: indirect; CPU: potentially high; memory: possible layer trade-off; bundle size: no.

## 5. Initial Page Load

The source-defined sequence is:

1. The browser requests a Next.js route. Pages Router pages without `getServerSideProps` are eligible for pre-rendering; Gallery explicitly supplies build-time props through `getStaticProps`. Actual hosting mode and response headers are deployment-dependent.
2. The server returns the document shell and route HTML. `_document.js` adds the favicon and document metadata. Each page renders its content and shared components into the route output.
3. The browser loads Next runtime, the shared `_app` code, the route's page chunk, generated CSS, and page-specific chunks. Next normally splits page code; exact compressed chunk sizes and parse costs need a production build/bundle report.
4. `_app.js` applies the global Tailwind CSS and the two `next/font` families and renders the global loader. `next/font` self-hosts fonts generated at build time; there is no source evidence of a browser-side Google Fonts stylesheet request. Exact number/size of requested font files needs a production network trace.
5. `GlobalLoader` is server-rendered initially visible over the page and locks scrolling after hydration. On router readiness it begins warming route assets and hides once that set resolves or its 2-second fallback fires. It does not wait for `window.load`, all document images, or form/API work.
6. Priority images include the Navbar logo and, where present, `PageHero` image. Home/Contact share the hero PNG; About uses `team.jpg`; Gallery uses `g_bg.png`. Next Image transforms these sources under normal optimizer operation. The loader's native prewarmer requests raw URLs separately.
7. The shared Footer embeds Google Maps eagerly with high priority on every page. This is the only third-party content request found in the rendered shared component tree.
8. Contact and Careers API calls occur only after user submission. The frontend awaits the FastAPI response; the API sends mail through SMTP. This can affect form-submission response time, but it is not on initial page load or route navigation.

Likely LCP candidates are the PageHero image on Home/About/Contact/Gallery and the visible heading/content on text-led pages. The actual LCP element and duration are not measurable from source code alone. FCP, INP, CLS, TBT, TTI, image decode duration, request count, compressed transfer bytes, cache reuse, backend/SMTP latency, and main-thread long tasks also require runtime measurement. Not measurable from source code alone.

## 6. Loader Performance

- One loader exists: `frontend/components/GlobalLoader.jsx`, mounted in `_app.js` on all routes. There is no second page-specific loading overlay for navigation (form submission indicators are separate and user-triggered).
- It begins with `isLoading=true`, renders a fixed black full-viewport shell with the logo, animated SVG ring, “LOADING” text and dots, and calls `useScrollLock(isLoading)`. The page is rendered underneath the overlay; the loader itself intercepts pointer interaction while shown.
- After `router.isReady`, the loader warms the current route's configured critical images. It hides when they finish or after 2,000 ms. It does not wait for `window.load`, every image, or API calls.
- On route start, it prewarms that route's listed assets and schedules a 2,000 ms fallback before showing the loader. If the route completes after the fallback appears, `gateLoaderForRoute` can then wait up to another 2,000 ms for configured images. If navigation completes before the fallback, it gates on those assets without showing the overlay first.
- On route error, it clears timers and hides the overlay. The current Home route gate includes all client logos; Services and Training have mismatched image entries; global background warmup covers assets from multiple routes.
- Recommendation: preserve this intended loader and its animation. Correct the asset sets, avoid gating on non-visible imagery, avoid raw/optimized duplicate downloads, and test the two-second route-fallback behavior under throttled network and failed-image conditions. Any adjustment to timing should be based on those tests, not an arbitrary shorter timer.

## 8. JavaScript / Bundle Optimization

- Per-route Pages Router splitting is already the main code-splitting mechanism. The eight pages are separate modules; avoid rewriting the app architecture.
- `GlobalLoader`, Navbar, and Footer are shared and run/render on every route. The highest shared runtime/network cost found is the Footer's map iframe, not a large JavaScript dependency.
- `gsap` is in `frontend/package.json`, but no frontend source imports it. It therefore does not appear necessary in the current browser dependency graph. Confirm no external script/build workflow uses it, then remove it from the manifest/lockfile in a later implementation phase if unused. Expected browser bundle reduction is likely none because it is not imported; the benefit is dependency/install footprint. Priority P3.
- `libphonenumber-js` is used by the Contact and Careers forms, not globally. Keep its validation/country behavior; measure route chunks and Careers module initialization before considering a narrower import or deferred list construction.
- `frontend/components/StatBar.jsx` updates four counters with `requestAnimationFrame` for two seconds after the section intersects. This is limited to Home and only runs when visible; no source evidence justifies removing the effect.
- `IntersectionObserver` use is limited to reveal/visibility work in page components. Counts are not by themselves evidence of a performance defect. Profile low-end devices before consolidating observers.
- `frontend/data/siteData.json` is imported as static data. There are no startup API requests or sequential data dependencies to optimize.
- Exact route chunk sizes, hydration cost, code duplication after tree-shaking, and interaction latency are not measurable from source code alone; inspect a production build and browser performance trace.

## 9. CSS Optimization

- `frontend/styles/globals.css` is a compact global stylesheet (about 260 source lines) with one Tailwind import, design tokens, loader/reveal/marquee rules, reduced-motion handling, and focus styles. No large duplicate CSS imports, remote `@import`, or obviously oversized selector rules were found.
- Tailwind v4/PostCSS generates the utility CSS; generated production CSS size and unused rule elimination must be checked in build output. Avoid manually deleting utilities based on source scans.
- Potential paint-heavy recurring work is localized to loader glow/drop-shadow, loader stroke-dash animation, and animated dots. This is measurement-gated in section 4.7; do not remove branded motion based only on inspection.
- Client and Training routes contain substantial route-local animation styles and decorative SVGs. Those styles are page-scoped rather than a separate external stylesheet. Profile frame/paint time on low-end devices before changing motion or artwork.
- Navbar and modal overlays use backdrop blur. No source evidence proves that the current blur causes a user-visible issue; inspect GPU/raster traces before altering it.
- No broad CSS minification recommendation is made: production optimization is a Next/Tailwind build responsibility and the source CSS is not evidently the dominant bottleneck.

## 10. Mobile Optimization

- Address eager external and below-fold images first: global Footer map, all Gallery images, Services rows, Training showcase, and below-fold Home/Clients logos.
- Serve portrait/phone-width image variants rather than desktop originals; preserve the exact `object-cover` crop and fixed frames. `next/image` already provides an appropriate mechanism on PageHero/Gallery; raw image usage in Services, Training, and Clients needs equivalent responsive sources.
- Avoid warming all client logos and other routes' hero images on a data-constrained or low-memory device. Preserve quick route behavior by keeping only the current visible hero/first-screen assets critical.
- Profile the loader animations and the Careers country-list setup on low-end Android before changing them. Static source does not establish CPU/GPU impact.
- Verify tap navigation and route transitions with the current full-screen loader after changing its asset gate. Keep reduced-motion support already present in global styles and route-local styles.
- Mobile-specific LCP, memory pressure, decoded image count, and tap responsiveness are not measurable from source code alone.

## 11. Slow Network Optimization

Resource scheduling should preserve the same content while reducing competition:

- Slow 3G: avoid the Google Maps iframe and offscreen gallery/service/training/client images until near view; request a suitably small hero/logo representation; do not let unrelated warmed assets gate the loader. First visible text and the actual route hero should get network priority.
- Fast 3G: use responsive image widths and lazy loading for below-fold sections; restrict high priority to genuinely visible content. Keep the map deferred and preserve the existing route fallback for navigation.
- Slow 4G: deliver WebP/AVIF or optimized JPEG where visual QA permits; avoid all-logo/all-gallery eager scheduling and raw-plus-optimized duplicate downloads. Ensure the first visible image is still promptly fetched.

These are scheduling recommendations, not claims of measured download time. The current app has no initial JSON/API waterfall dependency; contact/career network requests begin only after form submission.

## 14. Caching / Browser Optimization

- No service worker, application cache, explicit cache headers, CDN config, proxy config, or deployment manifest was found. Production cache policy cannot be determined from this repository alone.
- Verify the production host gives long-lived immutable caching to fingerprinted `/_next/static` build assets and sensible caching to Next Image optimizer output. Confirm HTML is revalidated appropriately on deploy.
- Public asset URLs are stable names (for example `hero_bg.png`), not content-hashed. If public files are cached for a long time, use deployment/version-aware invalidation or versioned filenames so an updated image does not remain stale. ## 15. Recommended Implementation Order

### Phase 1 — Safest/highest impact
1. Defer the Footer Google Maps iframe while preserving its current dimensions and content.
2. Correct loader critical-asset lists (`/services` and `/training` do not render their mapped images); stop using all Home client logos as loader gates.
3. Lazy-load Gallery images below the initial viewport while retaining every card and lightbox behavior.
4. Change Services and Training photos to responsive optimized output and near-viewport loading; retain existing crops and all placements.

### Phase 2 — Reduce critical image bytes
1. Visually QA and adopt the existing `hero_bg.webp` / `kess_logo.webp` candidates where they match the current image quality and transparency.
2. Resize/encode the About `team.jpg` source and large gallery/service/training photographs for the real rendered widths.
3. Make Home marquee and Clients grid logo priorities reflect actual visibility; preserve repeated marquee tracks and both marquee sections.

### Phase 3 — Loader and route performance
1. Ensure image warmup targets the same optimized output used by rendered components and does not fetch all routes' assets on every visit.
2. Validate loader lifecycle and fallback on initial load, successful navigation, slow route load, image failure, and client-side back/forward navigation.
3. Profile the loader's filter/SVG animation on low-end Android; tune only if the trace confirms recurring paint cost and visual comparison passes.

### Phase 4 — Measurement-led cleanup
1. Capture production page-chunk sizes and Careers/Contact CPU traces; only then consider phone-library/country-list changes.
2. Confirm `gsap` is unused in build/deployment tooling before removing the dependency.
3. Validate CDN cache/compression headers and repeat-visit behavior with the production host.
4. Run throttled browser tests and Core Web Vitals after the above changes. Do not set target Lighthouse scores until a baseline has been measured.
